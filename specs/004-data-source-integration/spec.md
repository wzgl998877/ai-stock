# Feature Specification: 多数据源股票数据体系引入

**Feature Branch**: `004-data-source-integration`
**Created**: 2026-04-24
**Status**: Draft
**Input**: User description: "结合 Code_Analysis_Report.md 分析报告，引入这些数据源以及数据，把股票相关的数据都采用这一套实现，可以先不用实现定时任务，定时任务在前端加一个同步侧边栏就好"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 手动触发数据同步 (Priority: P1)

用户在前端同步侧边栏中，选择数据源类型（Tushare / AKShare / BaoStock）和数据类型（股票基础信息、实时行情、历史K线、财务数据），点击"同步"按钮后，系统从对应数据源拉取数据并存入数据库。

**为什么是这个优先级**: 这是整个功能的核心价值——让用户能够按需手动拉取股票数据，没有这一步后续所有分析都无法进行。

**独立可测性**: 可以通过选择任意数据源+数据类型组合触发同步，验证数据是否成功存入数据库并可查询。

**验收场景**:

1. **Given** 用户已配置好 Tushare API Key，**When** 用户在侧边栏选择"Tushare → 股票基础信息"并点击同步，**Then** 系统显示同步进度，完成后数据库中可查询到最新数据
2. **Given** 用户未配置某数据源的 API Key，**When** 用户选择该数据源并尝试同步，**Then** 系统提示"请先配置该数据源的 API 密钥"
3. **Given** 同步正在进行中，**When** 用户查看侧边栏，**Then** 用户能看到实时进度条和当前同步状态

---

### User Story 2 - 查看同步状态与历史 (Priority: P2)

用户在同步侧边栏中可以查看历次同步任务的执行状态（成功/失败/进行中）、同步时间、数据源类型和数据量。

**为什么是这个优先级**: 用户需要了解同步是否成功，以及数据的新鲜度，这是数据可信度的基础保障。

**独立可测性**: 即使没有新同步任务，用户也可以查看历史同步记录，验证状态展示是否准确。

**验收场景**:

1. **Given** 用户已完成过一次同步，**When** 用户打开同步侧边栏，**Then** 列表中显示该次同步的时间、数据源、状态和数据量
2. **Given** 某次同步任务失败，**When** 用户查看该记录，**Then** 显示失败原因和错误信息

---

### User Story 3 - 数据查询与验证 (Priority: P3)

用户在同步完成后，可以通过现有的个股分析页面查询已同步的股票数据，验证数据是否正确入库。

**为什么是这个优先级**: 数据同步的最终目的是为分析提供数据支撑，用户需要能便捷地查看和验证数据。

**独立可测性**: 在已有个股分析页面输入股票代码，验证是否能查询到同步后的数据。

**验收场景**:

1. **Given** 用户已同步某股票的基础信息和历史K线，**When** 用户在分析页面输入该股票代码，**Then** 页面展示该股票的完整信息
2. **Given** 某股票存在多个数据源的数据，**When** 用户查看该股票数据，**Then** 系统按优先级（Tushare > AKShare > BaoStock）展示数据

---

### User Story 4 - 配置数据源密钥 (Priority: P2)

用户在系统设置页面中配置和管理各数据源的 API 密钥（Tushare Token、AKShare 无需密钥、BaoStock 账号等）。

**为什么是这个优先级**: 数据源配置是同步的前提条件，但没有同步功能本身，配置页面也没有意义，故排在 P2。

**独立可测性**: 用户可以独立地添加、修改、删除数据源配置，配置完成后保存至数据库。

**验收场景**:

1. **Given** 用户进入数据源配置页面，**When** 用户输入 Tushare Token 并保存，**Then** 配置加密存储到数据库，页面显示"配置成功"
2. **Given** 用户已有某数据源配置，**When** 用户修改该配置并保存，**Then** 配置被更新

---

### Edge Cases

- 当同步过程中 API 接口限流或超时，系统应暂停当前任务并提示用户，支持手动重试
- 当同一数据源的同步任务被重复触发时，系统应提示"当前数据源同步任务正在进行中"，防止重复执行
- 当数据库连接中断时，已拉取的数据应缓存到内存，连接恢复后继续写入
- 当用户同步历史K线时指定了超大时间范围（如10年），系统应提示用户确认，避免超时
- 当多个数据源同时触发同步时，系统应排队执行，避免资源竞争

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持 Tushare、AKShare、BaoStock 三个数据源的数据接入
- **FR-002**: 系统 MUST 支持四种数据类型的同步：股票基础信息、实时行情、历史K线、财务数据
- **FR-003**: 系统 MUST 在前端提供同步侧边栏，用户可在其中选择数据源、数据类型并触发同步
- **FR-004**: 系统 MUST 在同步过程中向用户展示实时进度（已处理数量/总数量、当前状态）
- **FR-005**: 系统 MUST 记录每次同步任务的执行状态、时间、数据源、数据量，并提供历史查询
- **FR-006**: 系统 MUST 支持用户在前端配置和管理各数据源的 API 密钥
- **FR-007**: 系统 MUST 将同步数据存储到 MongoDB 数据库中，遵循已有集合结构（stock_basic_info、market_quotes、stock_daily_quotes、stock_financial_data）
- **FR-008**: 系统 MUST 在数据写入时标注数据来源字段（source / data_source），支持多数据源共存
- **FR-009**: 系统 MUST 在数据写入前进行清洗和标准化（代码补零、日期格式化、单位转换等）
- **FR-010**: 系统 MUST 在同步失败时提供错误原因展示和手动重试能力
- **FR-011**: 系统 MUST 防止同一数据源的重复同步任务同时执行
- **FR-012**: 系统 MUST 在读取数据时按数据源优先级（Tushare > AKShare > BaoStock）返回结果
- **FR-013**: 系统 MUST 支持 Redis 作为缓存层，缓存热数据并设置合理的 TTL
- **FR-014**: 系统 MUST 在 Redis 不可用时自动降级到 MongoDB 直接读取

### Key Entities

- **数据源配置**: 包含数据源类型（Tushare/AKShare/BaoStock）、API 密钥/凭证、启用状态、优先级
- **股票基础信息**: 股票代码、名称、行业、上市日期、市场类型（A股/港股/美股）
- **实时行情**: 股票代码、当前价、涨跌幅、成交量、成交额、时间戳
- **历史K线**: 股票代码、交易日期、开盘价、最高价、最低价、收盘价、成交量、成交额、周期（日线/周线/月线）
- **财务数据**: 股票代码、报告期、财务指标（ROE、净利润、营收等）
- **同步任务**: 任务 ID、数据源、数据类型、状态（待执行/进行中/成功/失败）、开始时间、结束时间、数据量、错误信息

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户可以在 3 次点击内完成一次数据源选择和同步触发
- **SC-002**: 单只股票基础信息同步在 5 秒内完成
- **SC-003**: 同步过程中用户始终能看到进度反馈，无"卡死"感（每 2 秒至少更新一次状态）
- **SC-004**: 同步失败时，95% 的情况下用户能看到明确的错误原因
- **SC-005**: 多数据源共存时，数据读取优先级正确率 100%（按 Tushare > AKShare > BaoStock）
- **SC-006**: 同步完成后，用户可在个股分析页面成功查询到同步数据的比例达到 100%

## Assumptions

- 目标用户为有一定投资研究经验的用户，熟悉股票数据概念
- MongoDB 和 Redis 已部署且可正常连接（沿用项目现有配置）
- Tushare API 需要有效的 Token，AKShare 为开源免费库无需密钥，BaoStock 需要注册账号
- 本项目不实现自动定时同步，所有同步均由用户手动触发
- 历史数据量较大时（如全市场10年日线数据），同步可能耗时较长（数分钟），用户应被告知等待
- 数据源 API 的可用性和响应速度不受本项目控制，可能存在限流或暂时不可用的情况
- 现有个股分析页面（模块 003）已实现，本功能为其提供数据源支撑
