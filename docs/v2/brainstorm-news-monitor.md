# 头脑风暴：投资事件影响雷达

**日期**: 2026-05-11
**背景**: 基于现有 AI 股票分析平台（模块一 AI 分析 + 模块二 行情数据 + 模块三 数据工具），新增「投资事件影响雷达」模块
**核心命题**: **系统比用户更早发现——哪些事件正在影响他的投资**

---

## 一、机会理解

### 一个核心洞察

散户的真实困境不是"看不到新闻"，而是**不知道哪条新闻会影响自己的持仓**。

每天数百条财经新闻从他眼前划过——刷同花顺、刷东财、刷雪球——他真正需要知道的只有 3-5 条。但他不知道是哪 3-5 条。他要么错过了关键信息，要么花了大量时间刷了个寂寞。

**我们要做的不是"帮用户看更多新闻"，而是"告诉用户：这件事正在影响你的投资，你需要关注"。**

### 当前系统的能力缺口

| 能力 | 现状 | 缺口 |
|------|------|------|
| 事件分析 | 模块一已有对话式事件分析（系统A），支持 5 种事件类型 | **用户必须主动输入事件**，系统不会自己发现事件 |
| 新闻搜索 | 已有 3 个搜索引擎 + 多维度情报搜索 | **按需搜索**，用户不触发就没有 |
| 个股分析 | 模块一已有 13 Agent 深度分析（系统B），新闻分析师 Agent 可搜索新闻 | 每次分析实时搜索，**不缓存、不复用**，且是用户触发的 |
| 自选股行情 | 模块二已有实时行情 + 30 秒刷新 | **只有价格数据**，没有"为什么涨/跌"的归因 |
| 搜索缓存 | Redis 缓存搜索结果（TTL 600s） | 短暂缓存，无法积累事件知识 |

### 核心转变：从「用户找事件」到「事件找用户」

```
现状：用户看到新闻 → 想起来去分析 → 手动输入 → 系统分析 → 看结果
目标：系统自动发现事件 → 判断对用户投资的影响 → 主动告诉用户 → 一键深度分析
```

这是本质区别。原来的流程，**起点是用户**。新的流程，**起点是系统**。

### 竞品差异化的切入点

新浪财经、同花顺、东方财富做的是"让所有人看到所有新闻"。我们做的是：

**"系统替你盯着，有事才叫你"** — 系统知道你持有哪些股票、关注哪些行业、分析过哪些事件，当影响你投资的事件发生时，主动告诉你。

| 维度 | 头部平台 | 我们 |
|------|----------|------|
| 信息流向 | 广播式（所有人看一样的内容） | 窄播式（只推和你投资相关的） |
| 时效性 | 人工编辑推荐，有延迟 | AI 自动发现 + 自动关联，秒级 |
| 深度 | 新闻原文 + 简单标签 | AI 影响解读 + 历史分析联动 |
| 个性化 | 基于浏览行为的推荐 | 基于自选股 + 知识库的精准匹配 |
| 行动闭环 | 看完就完了 | 一键触发模块一的事件/个股分析 |

**我们的独有壁垒**：头部平台没有用户的个人分析数据（知识库），无法知道"这个用户上周分析过新能源补贴，今天这条新闻和那个分析相关"。我们有。

## 二、PM 视角：5 个功能想法

### PM-1：投资影响雷达面板（核心 MVP）

**想法**: 系统持续监测财经信息源，自动识别可能影响用户自选股的事件，以"影响面板"形式展示当前正在发生的投资影响。

**为什么做**: 这是整个模块的核心价值——**系统比用户更早知道**。用户打开系统第一眼看到的不是"今天的新闻"，而是"此刻正在影响你投资的事件"。

**面板信息架构**:

```

**核心逻辑**:
1. 系统持续从信息源获取最新财经信息
2. 每条信息自动执行：提取关联股票/行业 → 匹配用户自选股 → 判断影响方向和程度
3. 只有与用户自选股相关的事件才出现在面板上
4. 按"正在影响"和"今日已影响"分层展示

**关键假设**:
- 自选股 ≤ 30 只，每日相关影响事件 ≤ 10 条，信息量高度可控
- AI 判断"是否影响用户投资"的准确率 ≥ 80%
- 用户打开面板后 5 秒内就能知道"今天有什么在影响我的投资"

**与现有系统的协同**:
- 自选股数据直接复用（`t_watchlist_group` / `t_watchlist_item`）
- 事件影响分析复用模块一的 5 套事件类型模板和提示词
- "一键分析"直接调用模块一的事件分析系统A
- 知识库联动复用 `t_article_stock` / `t_article_industry` 的关联逻辑

### PM-2：投资影响预警推送（核心差异化）

**想法**: 当系统识别到**高置信度**的投资影响事件时，主动推送预警，而不是等用户来面板看。

**为什么做**: 面板是"拉"模式（用户来看），预警是"推"模式（系统告诉你）。核心命题"系统比用户更早发现"要求我们做**推模式**。用户可能正在上班、正在做别的事，但影响他投资的事件已经发生了——他应该第一时间知道。

**预警触发条件**（按优先级）:
- **P0 紧急**：自选股直接出现在事件中心（如：宁德时代发布重大公告）→ 立即推送
- **P1 重要**：自选股所属行业出现重大政策/事件（如：新能源汽车补贴政策调整）→ 5 分钟内推送
- **P2 关注**：自选股间接相关的事件（如：上游原材料价格波动）→ 纳入面板，不单独推送

**预警消息格式**:
```
🔔 投资影响预警

国际油价突破 85 美元/桶，创近 3 个月新高

影响你的投资：
· 中国石油(601857) ▲ 利好 · 置信度 85%
· 中国石化(600028) ▲ 利好 · 置信度 78%

你曾在 4/15 分析过类似事件 →《中东局势对能源板块影响》

[查看详情]  [一键分析]  [忽略此类]
```

**关键假设**:
- 每日 P0+P1 预警 ≤ 5 条（多了就是噪音，用户会关通知）
- 预警到推送的延迟 ≤ 5 分钟（从信息源获取到完成影响判断）
- 用户收到预警后的点击率 ≥ 40%（因为精准匹配自选股）

**与现有系统的协同**:
- 预警的"一键分析"直接跳转模块一事件分析，**预填事件内容**
- 预警历史记录可回溯，与知识库分析文章关联

### PM-3：影响晨报（每日启动仪式）

**想法**: 每天早上 7:00 自动生成个性化"影响晨报"——不是泛泛的新闻早报，而是**昨晚到今晨，有哪些事件在影响你的投资**。

**为什么做**: 这是用户每天打开系统第一个看到的内容。区别于头部平台的"7x24 快讯"（所有人看一样的），我们的晨报只说**和你投资相关的事**。用户花 30 秒扫一眼就知道"今天开盘要注意什么"。

**晨报结构**:
```

- 每日影响事件 ≤ 10 条，用户 30 秒可扫完

**与现有系统的协同**:
- 自选股行情数据复用（`t_market_quote`）
- 事件影响判断复用模块一的事件分析提示词
- 知识库历史分析可引用（"你之前分析过类似事件..."）

### PM-4：事件影响追溯（知识增强闭环）

**想法**: 当影响事件发生后，系统不仅告诉你"发生了什么"，还追溯"这件事和你之前的分析有什么关系"。

**具体联动**:
- 影响事件卡片下方自动展示："你 3/28 分析过 →《新能源补贴政策影响》，本次事件与该分析相关度 85%"
- 知识库文章底部增加"最新相关影响事件"区域（让历史分析活起来）
- 每周自动生成"影响回顾"：本周影响你投资的事件 + 你之前分析的结论 + 实际走势对比

**为什么做**: 这是连接"事件发现"和"知识库"的桥梁。用户之前的分析不是废纸，而是系统的**个性化知识底座**。头部平台没有用户的分析数据，做不了这个——这是我们的**独有壁垒**。

**更深层的价值**: 用户做了分析 → 知识库积累了认知 → 系统基于这些认知更好地判断影响 → 形成正循环。系统越用越懂你。

**关键假设**:
- 事件-文章关联准确率 ≥ 75%（基于行业 + 股票代码 + 事件类型匹配）
- 用户看到"你之前分析过"后的点击率 ≥ 30%
- 影响追溯让用户觉得"系统真的懂我的投资"

---

### PM-5：影响范围配置

**想法**: 用户可以定义"哪些事件算影响我的投资"，让系统的判断更贴合个人需求。

**可配置项**:
- **关注的股票**：除了自选股，还可以额外关注特定股票
- **关注的行业**：从申万 31 个一级行业中选取
- **关注的事件类型**：政策法规 / 公司公告 / 行业动态 / 宏观经济 / 地缘政治
- **预警灵敏度**：高（所有相关事件都推）/ 中（只推高置信度）/ 低（只推直接影响）
- **免打扰时段**：如 22:00 - 7:00 不推送

**为什么做**: 系统的判断不可能 100% 准确，让用户有调整的权力。但默认配置就要足够好（开箱即用 ≥ 80% 满意度），配置只是锦上添花。

- 行动区的每个按钮都有明确的下游目的地

**为什么不单独做页面**: 减少页面跳转，让用户在自选股页面就能同时看到"行情 + 什么在影响行情"。

## 四、工程师视角：5 个功能想法

### E-1：事件采集与影响判断管线（核心引擎）

**想法**: 构建"信息采集 → 事件提取 → 影响判断"的完整管线，这是整个模块的核心引擎。

**技术设计**:
```
┌──────────────────────────────────────────────────────────────┐
│                    EventImpactPipeline                        │
│                                                              │
│  ┌─────────────┐                                             │
│  │ 信息源采集   │  财联社/东财/新浪/证券时报 + 现有3个搜索引擎 │
│  └──────┬──────┘                                             │
│         ↓                                                    │
│  ┌─────────────┐                                             │
│  │ 事件去重聚合 │  URL去重 → 标题相似度 → 归并为同一事件       │
│  └──────┬──────┘                                             │
│         ↓                                                    │
│  ┌─────────────────────────────┐                             │
│  │ 影响判断引擎（核心）          │                             │
│  │                             │                             │
│  │ ① 提取关联股票/行业          │  复用 MetadataExtractor     │
│  │ ② 匹配用户自选股/关注行业    │  查 t_watchlist_item       │
│  │ ③ 判断影响方向 + 置信度      │  规则引擎 + LLM 兜底       │
│  │ ④ 计算影响优先级 (P0/P1/P2) │  基于置信度+影响范围        │
│  └──────┬──────────────────────┘                             │
│         ↓                                                    │
│  ┌─────────────┐     ┌─────────────┐                        │
│  │ 入库 t_event │     │ 触发预警推送 │  (P0/P1 时触发)       │
│  └─────────────┘     └─────────────┘                        │
└──────────────────────────────────────────────────────────────┘
```

**调度策略**:
- 交易时段（9:00-15:00）：每 10 分钟采集一次，影响判断实时执行
- 非交易时段：每 1 小时采集一次
- 晨报生成：每天 6:30 触发，聚合隔夜到今晨的所有影响事件

**影响判断引擎详解**:
```
输入：一条新闻/事件（标题 + 摘要 + 来源）

Step 1: 关联提取（复用 MetadataExtractor）
  → 提取股票代码/名称、行业关键词

Step 2: 用户匹配
  → 关联的股票是否在用户的自选股中？
  → 关联的行业是否在用户的关注行业中？
  → 匹配结果 = 影响到的具体自选股列表

Step 3: 影响判断
  → 规则引擎（快速）：
     关键词匹配利好/利空词汇库 → sentiment + confidence
  → LLM 兜底（对规则引擎低置信度的）：
     调用 LLM 判断影响方向和原因

Step 4: 优先级计算
  → P0: 直接涉及自选股 + 置信度 > 80% + 重大事件
  → P1: 涉及关注行业 + 置信度 > 70%
  → P2: 其他相关事件

输出：ImpactEvent {
  event_id, title, summary,
  affected_stocks: [{code, name, direction, confidence, reason}],
  affected_industries: [{name, direction}],
  priority: P0/P1/P2,
  user_id  ← 每个用户独立计算
}
```

**复用现有基础设施**:
- APScheduler 已引入
- Redis 缓存复用
- BeautifulSoup 已在用
- SearchService 多引擎搜索可复用
- MetadataExtractor 股票/行业提取逻辑直接复用
- 模块一的事件分析提示词模板可复用

---

### E-2：事件去重与聚合引擎

**想法**: 多源采集后，同一事件会有多篇报道，需要去重和聚合。

**技术方案**:
- **精确去重**：URL 去重（MD5 hash）
- **语义去重**：标题相似度（Jaccard 相似度 / TF-IDF 余弦相似度，阈值 0.7）
- **事件聚合**：相似新闻归为同一"事件"，选择最早或最权威的来源作为主条目
- **来源计数**：同一事件被多个来源报道，source_count 增加（source_count ≥ 3 标记为"热点事件"）

**数据模型**:
```sql
t_impact_event (影响事件)
  - event_id
  - title (事件标题)
  - summary (AI 生成摘要，≤200字)
  - event_type (geopolitical/policy/earnings/industry/macro/other)
  - sentiment (positive/negative/neutral)
  - importance (high/medium/low)
  - affected_industries (JSON, 关联行业 + direction)
  - affected_stocks (JSON, 关联股票 + direction + confidence)
  - source_count (来源数量)
  - first_seen_at (首次发现时间)
  - last_seen_at (最后更新时间)

t_impact_article (事件原始报道)
  - article_id
  - event_id (关联事件)
  - title
  - content (摘要 ≤ 500字，不存全文)
  - source (来源网站)
  - url
  - url_hash (去重用)
  - published_at
  - crawled_at

t_user_impact (用户-事件影响关联，每用户独立)
  - id
  - user_id
  - event_id
  - matched_stocks (JSON, 匹配到的自选股)
  - priority (P0/P1/P2)
  - is_read (是否已读)
  - created_at
```

**与现有系统的关系**:
- 影响事件与 `t_article_stock` 共享股票关联逻辑
- 影响事件与 `t_article_industry` 共享行业关联逻辑
- `t_user_impact` 的 `matched_stocks` 引用 `t_watchlist_item`

---

### E-3：用户投资画像与影响匹配

**想法**: 为每个用户构建"投资画像"，影响判断基于画像精准匹配。

**用户投资画像**:
```
UserInvestmentProfile {
  watchlist_stocks: [      ← 来自 t_watchlist_item
    {code: "300750", name: "宁德时代", added_at: "2026-03-15"},
    {code: "601857", name: "中国石油", added_at: "2026-04-01"},
    ...
  ],

  analysis_history: [      ← 来自 t_analysis_article + t_article_stock
    {article_id, title, stocks: [...], industries: [...], analyzed_at},
    ...
  ],

  focused_industries: [    ← 从分析历史 + 自选股行业自动推断
    "电力设备", "石油石化", ...
  ],

  recent_signals: [        ← 来自 t_stock_analysis 的信号提取
    {stock_code, signal_type, signal_time},
    ...
  ]
}
```

**匹配逻辑**:
1. 事件的 `affected_stocks` 与用户的 `watchlist_stocks` 取交集 → 直接影响
2. 事件的 `affected_industries` 与用户的 `focused_industries` 取交集 → 间接影响
3. 事件的语义与用户的 `analysis_history` 相似度 → 知识库联动

**为什么需要画像**: 不同用户的自选股不同，同一个事件对不同用户的影响完全不同。比如"油价上涨"对持有中国石油的用户是利好，对持有航空股的用户是利空。系统必须**按用户**计算影响。

### E-4：影响晨报 LangGraph 工作流

**想法**: 晨报不是简单的事件列表拼接，而是 LangGraph 驱动的 AI 编排流程。

**工作流设计**:
```
START
  → collect_impact_events (收集过去24小时影响该用户的事件)
  → collect_portfolio_status (收集自选股行情变化)
  → match_knowledge_context (匹配知识库历史分析，计算关联度)
  → generate_morning_briefing (LLM 生成晨报)
  → save_briefing (持久化到 t_morning_briefing)
  → notify_user (标记为待推送)
  → END
```

**优势**:
- 复用 LangGraph 框架（项目已引入，团队熟悉）
- 晨报内容来自本地数据库（已缓存的影响事件），不依赖实时采集
- 每个用户的晨报独立生成，100% 个性化
- 知识库匹配环节让晨报具备"认知深度"——不是泛泛而谈

### E-5：统一信息源抽象层

**想法**: 定义统一的信息源接口，不同来源只需实现该接口即可接入。

**接口设计**:
```python
class BaseEventProvider(ABC):
    """信息源统一抽象"""

    @abstractmethod
    async def fetch_latest(self, count: int) -> list[RawEventItem]:
        """获取最新资讯"""

    @abstractmethod
    async def fetch_by_stock(self, stock_code: str, count: int) -> list[RawEventItem]:
        """按股票代码获取资讯"""

    @abstractmethod
    async def fetch_by_keyword(self, keyword: str, count: int) -> list[RawEventItem]:
        """按关键词搜索资讯"""
```

**已可适配的信息源**:
- Tavily / Anspire / Bocha → 适配为 EventProvider（已有搜索能力）

**需新增的信息源**:
- 财联社快讯（API/RSS）— 金融信息最快来源
- 东方财富资讯（HTML 爬取）— 信息量最大
- 新浪财经 RSS — 传统大厂覆盖
- 巨潮资讯网（公告类）— 公司公告官方来源

## 五、Top 5 优先级排序

### 优先级评估标准

| 维度 | 权重 | 说明 |
|------|------|------|
| 核心命题契合度 | 40% | 是否直接解决"系统比用户更早发现影响"这个核心问题？ |
| 可验证速度 | 25% | 能否快速上线验证？ |
| 差异化潜力 | 20% | 头部竞品是否容易复制？ |

### Top 5 排序

---

#### #1 🥇 投资影响雷达面板（PM-1 + D-1 + E-1 + E-2 + E-3）

**核心命题契合度**: 极高 — 这就是"系统比用户更早发现影响"的直接载体。用户一打开系统，就看到"此刻有什么在影响你的投资"。

**差异化**: 头部平台没有用户的自选股+知识库数据，做不到"只展示和你投资相关的事件"。

**验证速度**: MVP 可复用现有 3 个搜索引擎采集信息 + MetadataExtractor 关联股票 + 简单规则判断影响方向，2-3 周可出 demo。

**协同价值**: 极高 — 面板中每条影响事件都可以一键跳转模块一进行深度分析，直接拉动核心功能使用。

**关键假设需验证**:
1. 系统发现影响事件 → 用户看到面板的延迟 ≤ 15 分钟（用户觉得"及时"）
2. 影响事件与自选股的匹配准确率 ≥ 80%（匹配错了用户会失去信任）
3. 每日影响事件 ≤ 10 条（多了用户不看，少了用户觉得没用）
4. 用户打开面板的频率 ≥ 每天 2 次

**MVP 范围**:
- 后端：信息采集调度 + 去重 + MetadataExtractor 关联 + 规则引擎影响判断 + 用户画像匹配
- 前端：影响雷达面板页面（正在影响 + 今日已影响 + 影响概览）
- 信息源：复用现有 3 个搜索引擎，暂不新增爬虫
- 不含：预警推送（#2）、晨报（#3）

---

#### #2 🥈 投资影响预警推送（PM-2 + D-5）

**核心命题契合度**: 极高 — "系统比用户更早发现"的极致体现。用户不需要打开系统，系统主动告诉他。

**差异化**: 头部平台的推送是"热门新闻推送"（所有人都收到一样的），我们的是"投资影响推送"（只有影响你自选股的才推）。

**验证速度**: 依赖 #1 的影响判断引擎，只需增加推送触发逻辑 + 前端通知组件。

**协同价值**: 高 — 预警是"拉"用户进入系统的钩子，推送后的一键分析直接进入模块一。

**关键假设需验证**:
1. 每日预警 ≤ 5 条（多了用户关通知，就废了）
2. 预警准确率 ≥ 75%（推送了无关事件，用户会关通知）
3. 预警 → 用户点击率 ≥ 40%（低于此说明不够精准）
4. 预警 → 一键分析的转化率 ≥ 15%（这是核心价值链）

**MVP 范围**:
- 后端：P0/P1 优先级判断 + 推送触发逻辑
- 前端：铃铛通知 + 影响事件摘要 Drawer
- 推送渠道：仅页面内通知（Phase 2 再做浏览器通知）

---

#### #3 🥉 影响晨报（PM-3 + D-2 + E-4）

**核心命题契合度**: 高 — 每日首次启动时的"投资影响摘要"，解决"昨晚发生了什么"。

**差异化**: 头部平台早报是通用的，我们的是**100% 个性化**的（只说和你投资相关的）。

**验证速度**: 依赖 #1 的影响事件数据，LangGraph 工作流模式团队已熟悉。

**协同价值**: 高 — 晨报底部"开始今日分析"入口直接进入事件分析，拉动模块一使用。

**关键假设需验证**:
1. 晨报 100% 个性化，每条内容都与用户投资相关
2. 用户 30 秒可扫完晨报核心信息
3. 晨报 → 点击分析按钮的转化率 ≥ 20%

**MVP 范围**:
- 后端：LangGraph 晨报生成工作流（6:30 定时触发）
- 前端：晨报展示页面（卡片式布局 + AI 一句话摘要）

---

#### #4 事件影响追溯与知识库联动（PM-4 + D-3）

**核心命题契合度**: 中高 — 不是"更早发现"，而是"发现后的深度价值"。

**差异化**: **独有壁垒** — 头部平台没有用户的个人分析数据，做不了这个。

**验证速度**: 依赖 #1 的影响事件数据 + 知识库关联匹配，可在 #1 之后快速实现。

**协同价值**: 极高 — 打通影响事件 ↔ 知识库的闭环，让系统"越用越懂你"。

**关键假设需验证**:
1. 事件-文章关联的匹配准确率 ≥ 75%
2. 用户看到"你之前分析过"后的点击率 ≥ 30%
3. 影响追溯功能让用户觉得系统有价值，而不仅仅是新闻推送

#### #5 影响范围配置（PM-5 + E-5）

**核心命题契合度**: 低 — 不直接影响"更早发现"的核心命题，是精细化工具。

**差异化**: 中 — 个性化配置是标配，不算强差异化。

**验证速度**: 相对独立，可并行开发。

**协同价值**: 中 — 主要是配置管理，让系统更精准。

**关键假设需验证**:
1. 默认配置就能满足 80% 用户需求（用户不想花时间配置）
2. 配置后系统精准度明显提升（让用户觉得配置值得）

## 六、推荐实施路径

```
Phase 0 (基础设施，1周):
  └── E-1 事件采集管线框架
  └── E-2 去重与聚合引擎
  └── E-3 用户投资画像 + 影响匹配
  └── E-5 信息源抽象层（先适配现有3个搜索引擎）

Phase 1 (核心价值，2-3周):
  └── #1 投资影响雷达面板
      （信息采集 → 影响判断 → 面板展示 → 一键分析）

Phase 2 (推模式，1-2周):
  └── #2 投资影响预警推送
      （P0/P1 判断 → 页面内通知 → 摘要 Drawer）
  └── #3 影响晨报
      （LangGraph 工作流 → 每日6:30生成 → 首屏展示）

Phase 3 (深度联动，持续):
  └── #4 事件影响追溯 + 知识库联动
  └── #5 影响范围配置
  └── D-3 事件详情页（AI完整解读）
  └── 新增信息源（财联社/东财/巨潮资讯）
```

**实施原则**:
- **先"拉"后"推"**：先做面板（用户来看），验证影响判断准确后，再做预警推送（系统主动推）
- **先规则后 AI**：影响判断先用关键词规则引擎（快、可控），验证流程跑通后再引入 LLM 增强
- **先复用后新建**：信息源先复用现有 3 个搜索引擎，验证价值后再投入做财联社/东财爬虫

## 七、风险与注意事项

| 风险 | 概率 | 应对 |
|------|------|------|
| 影响判断不准（推了无关事件） | 高 | MVP 先用规则引擎，精准优先于召回；用户可反馈"不相关"用于优化 |
| 信息源反爬（IP 封禁、验证码） | 高 | 控制采集频率（≥ 10 分钟间隔）；优先用 RSS/API；多 IP 轮换 |
| 版权合规（直接展示原文） | 中 | 只展示标题 + 摘要（≤ 200 字），点击跳转原文链接；AI 解读为原创内容 |
| 用户觉得"和新闻 App 没区别" | 中 | **核心差异化**在于"只展示影响你投资的事件"，不是新闻聚合。UI 上突出"影响你的：xxx" |
| 信息延迟（事件发生 → 用户看到 > 30 分钟） | 中 | 交易时段 10 分钟采集一次；P0 事件可考虑触发即时采集 |
| 数据库存储压力 | 低 | 事件正文仅存摘要（≤ 500 字），原文链接跳转；超过 30 天的事件自动归档 |

## 八、成功指标

如何判断这个模块是否成功？

| 指标 | 目标 | 衡量方式 |
